# C4 diagrams

Use with the shared workflow in [SKILL.md](../SKILL.md).

## Map code to C4

Keep one level per page: Context shows people and software systems; Container shows runnable applications and data stores within a system; Component shows major building blocks within one container. A boundary identifies the system or container being expanded, while neighboring people and systems provide context.

| In the code                                                                                                                                                                | Draw as                                                                                                               |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| User or role interacting with the system                                                                                                                                   | Person; use the external variant when outside the modeled organization                                                |
| Whole system or independently owned neighboring system                                                                                                                     | Software System; use the external variant for a neighboring system outside scope                                      |
| Runnable web app, API, service, worker, queue, or message broker                                                                                                           | Container, named for its actual role                                                                                  |
| Database or persistent data store                                                                                                                                          | Database container                                                                                                    |
| Framework-managed unit: Angular `@Component`/`@Injectable`/`@NgModule`, Spring `@Service`/`@Controller`, ASP.NET controller, Django app, Rails controller, NestJS provider | Component within the container being expanded; constructor-injected or declared dependencies become dependency arrows |
| HTTP/gRPC call, queue publish/consume, or DB driver call                                                                                                                   | Directed relationship describing the interaction and its evidenced technology                                         |

Top-level functions or modules with no class can be represented as Components. Do not turn every class into a Component when the page is a container overview.

## Native shapes and API names

Use Lucid's native **C4** library rather than recreating its elements with generic rectangles, flowchart database symbols, or custom-library lookalikes. Production shape discovery exposes these entries in library `c4.js`:

| C4 library name          | Exact `shapeId`                  | Appearance                                                                     |
| ------------------------ | -------------------------------- | ------------------------------------------------------------------------------ |
| Boundary                 | `C4BoundaryContainerBlock`       | Dashed rectangular container with its name/type caption inside the bottom edge |
| Person                   | `C4PersonBlock`                  | Blue person silhouette with text in the body                                   |
| External person          | `C4PersonBlock_External`         | Gray person silhouette                                                         |
| Software System          | `C4SoftwareSystemBlock`          | Blue rectangular block                                                         |
| External software system | `C4SoftwareSystemBlock_External` | Gray rectangular block                                                         |
| Container                | `C4ContainerBlock`               | Light gray rectangular block                                                   |
| Database                 | `C4DatabaseBlock`                | Light blue upright cylinder                                                    |
| Component                | `C4ComponentBlock`               | Light blue rectangular block                                                   |

These are **shape-library IDs**, not Standard Import `type` values. The `_External` entries are variants of the underlying person/system classes; passing the base class name loses the variant choice. There is no separate native C4 queue entry in this catalog: use Container with the broker/queue's name, technology, and responsibility.

Before creating shapes, call `lucid_get_script_catalog`, load `shapelibrary` and `basecanvasediting`, and browse:

```js
return await skills.shapelibrary.shapeLibrary({libraryId: 'c4.js', pageSize: 200});
```

Use the current result's exact `id` and `libraryId` in `basecanvasediting.createBlock`. If the catalog changes, follow its current entries. Do not choose the AWS EC2 “C4 Instance” search result or a custom “C4” library in place of the native library.

## Creation and text fields

The current Standard Import registry does not list dedicated C4 types or their separate text fields. Build native C4 content with `lucid_run_script`. For a new document, first read `lucid://skills/diagram-specification`, validate a minimal Standard Import document with the intended empty pages, and create it with `lucid_create_diagram_from_specification`, `product: "lucidchart"`, and `use_assisted_layout: false`. For example:

```json
{"version": 1, "pages": [{"id": "c4-context", "title": "System Context", "shapes": [], "lines": []}]}
```

Use the returned document ID for subsequent documentation loads and scripts. Read the document and call `getPages()` to obtain its actual page IDs before navigating or adding content. For an existing document, use its current pages and inspect affected items first.

Create native shapes with discovered IDs, preserving their default appearance and proportions. For example, after discovering this entry:

```js
const block = await skills.basecanvasediting.createBlock({
    shapeId: 'C4ContainerBlock',
    libraryId: 'c4.js',
});
return {id: block.id, validation: await skills.basecanvasediting.validateCanvas({itemIds: [block.id]})};
```

Then inspect returned item IDs in a separate read-only script before filling their text areas or planning final placement. Native C4 elements have three editable areas:

| Text area           | Content                                                                                                                                                                       |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TitleText`         | Name used in the code, or the person's role; for example `Order API`                                                                                                          |
| `SquareBracketText` | Bracketed type and evidenced technology: `[Person]`, `[Software System]`, `[Container: Node.js, Express]`, `[Container: PostgreSQL]`, or `[Component: Spring MVC Controller]` |
| `DescriptionText`   | Short responsibility from the source; for example `Accepts and validates orders`                                                                                              |

Confirm the keys in `inspect()` before writing them with `basecanvasediting.setText({itemId, textAreaName, text})`. Populate all three areas; setting only `label` changes the preferred area and leaves the other placeholders behind. Use plain text and actual newlines in scripting calls; HTML and Markdown markers are literal in `setText`. The native shapes provide their own title emphasis and alignment. Load the `text` script API only when additional rich-text styling is needed.

The Boundary uses its `Text` area for a two-line caption such as `Order System\n[Software System]` or `Order API\n[Container: Node.js, Express]`. Keep the caption inside the bottom edge clear of children and lines. Inspect its current fields rather than applying a generic container's `containerTitle` property.

Replace placeholders such as `Name`, `Technology`, `Description of the container`, and `Relationship`. Preserve each inference's `?` beside the affected name, technology, responsibility, or relationship claim, as required by the core skill.

## Relationships

Use directed, dashed connectors with no source cap and an arrow at the target. In the script API, use `createLine` with `shape: "elbow"`, `style: {strokeStyle: "dashed"}`, source endpoint `style: "None"`, and destination endpoint `style: "Arrow"`. Let Lucid route the line; use `rerouteLines` when needed. Script endpoint/style names differ from Standard Import's lowercase enums.

Every relationship needs a specific verb phrase describing what the source does with the target: `Submits orders`, `Reads and writes orders`, `Publishes order.created`, or `Consumes order.created`. Add evidenced communication technology on a second line, for example `Submits orders\n[HTTPS/JSON]` or `Publishes order.created\n[AMQP]`. Include the route, method, or event name when it helps distinguish relationships. Avoid vague `Uses` when the source establishes a more precise interaction.

At Context level, a human/business interaction can be labeled without an implementation protocol. At Container or Component level, include a protocol, interface, or in-process call mechanism when it is evidenced, or when it is explicitly inferred and marked with `?`. List inferred technologies as assumptions in the final message; if the technology is unknown and omitted, disclose that gap in the final message. Every relationship still needs a verb-phrase label. A REST client alone does not establish HTTPS, and a database product does not establish its driver or transport. Do not manufacture a protocol to fill a label.

Choose direction from the modeled interaction: caller to callee, writer to store, publisher to broker, consumer to broker for a labeled consumption dependency. If showing event delivery instead, use broker to consumer and label the delivery explicitly. Use separate labeled arrows when opposite directions represent distinct interactions; do not add response arrows to every dependency.

## Sizing and layout

- Start with native default sizes; people need more height than rectangular elements, and database text must fit below its rim. Keep elements of the same kind consistent in size and preserve native colors unless the user requested another style.
- Fill all text areas before final placement, since content can grow the shapes. Use inspected `footprint` geometry and `createBlockRelative`/`placeRelative` for spacing, following the core skill's clearance and padding rules. Reserve room for the boundary's bottom caption.
- Place people above or beside the system, related containers together, and external systems/data stores on the sides or bottom. Size boundaries for their actual children and captions. Use the core detail and page-splitting defaults.

## C4-specific verification

Apply Step 6 of the core skill, with these additional checks:

- Native C4 classes and external variants match the intended roles.
- All three text areas are populated and contain no default placeholders.
- Each page uses the intended C4 level and boundary membership.
- Person/database silhouettes retain their proportions, database text fits below the rim, and boundary captions remain unobscured.
